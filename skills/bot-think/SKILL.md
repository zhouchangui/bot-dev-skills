# /bot-think — 第一性原理审查与决策树多轮深度追问

目标：在动一行代码前，先验明功能必要性，再把需求建模为**决策树（Design Tree）按前沿（Frontier）多轮深挖到底**——主动挑刺术语歧义与极端边缘场景，做到**零静默假设**后再对齐视觉系统（若含界面）与备选架构路线，落盘精简设计稿、`GLOSSARY.md`、`DESIGN.md` 或 ADR（**严禁在本阶段写业务代码**）。

## 通用流控与极简铁律

1. **业务问透优先，按场景与题量分流（别乒乓，更不削足适履）**：澄清问题时每题给出默认推荐与理由，**严禁为迁就交互弹窗的题数/字数上限而合并、删减业务问题或把开放题硬改选择题**：
   - **`/bot-think` 决策树多轮追问、> 4 题、含开放性业务问题，或宿主无交互工具**：全程改用**正文分组编号清单**（`❓ Qn` + `➡️ 推荐`，标清默认推荐，支持用户按题号回“全默认，仅改第 N 题”），输出后**立即结束本轮等待用户回复**，严禁同轮混用截断式弹窗，严禁自问自答或替用户暗自拍板；
   - **方案拍板或下游阶段 ≤ 4 个独立离散选择题**：直接用宿主交互式多选工具一次点选。
2. **三道硬暂停闸门（未经用户明确同意，严禁自行执行）**：
   - **重大决策**：架构路线、模块公开契约/Schema 变更、不可逆 `One-way door` 变更、删减核心范围、引入新依赖或不可逆操作。
   - **创建分支或 worktree**：执行 `git checkout -b` / `git switch -c` / `git worktree add` 前必须先询问确认分支名与基线。
   - **发布与合并**：执行 `git push`、创建/合并 PR、发版构建或线上部署前必须先询问确认。
   其余探索、测试、局部重构与修 bug 连续推进，不要琐碎弹窗打断心流。
3. **极简编码与反退化四铁律（写任何代码前先过一遍）**：
   - **复用阶梯**：`仓库已有 helper / 模式 → 语言标准库 → 平台原生特性（如原生 HTML/CSS、DB 约束）→ 已安装依赖`，在最高一层能解决就止步，严禁未经确认新增包。
   - **三次法则（Rule of Three）**：同一逻辑未真实出现 3 次且无第二个真实调用方时，禁止提前抽工厂、策略类、通用配置层或猜测性抽象。
   - **零纯转发**：禁止写只透传参数的中间转发函数（Middle Man），禁止为不可能发生的内部状态写冗余兜底分支。
   - **严禁类型逃逸与假默认值投毒**：系统边界入参必须显式窄化校验，内部不变量损坏必须快速失败（Fail-Fast）；**严禁用双层类型强转（`as any` / `as unknown as T` / `@ts-ignore` / `# type: ignore`）消音，严禁用 `?? 0`、`?? ''`、`?? []` 把上游契约断裂静默吞成合法假数据**。
4. **宿主交互与工具映射**：采用宿主中立表达：读取/编辑文件、执行终端命令、代码库检索、向用户批量提问（≤4 个独立选择题用交互式多选工具；超 4 题、含开放性业务问题或无工具时用正文分组编号清单等待用户回复，业务问清楚优先）。

## 执行步骤

1. **事实归 Agent，绝不拿仓库已知事实烦用户（Facts vs Decisions）**：
   - 开口提问前，先扫描入口文档（`AGENTS.md` / `CLAUDE.md`）、领域术语表（`GLOSSARY.md` / `CONTEXT.md`）、`DESIGN.md` 与 `docs/adr/`；
   - 当某个前沿问题依赖代码库现状、现有接口签名或配置事实时，主动检索或派只读子代理查清（不阻塞其余独立问题的发问），**严禁把读代码就能确认的事实抛给用户回答**；但凡属业务规则、取舍与边界行为，**决定权 100% 归用户，严禁替用户暗自拍板**。
2. **第一性原理必要性审查（First-Principles Necessity Gate · 先审该不该做，勿私自砍题）**：
   - **剥离方案、还原根目标（反 XY Problem）**：把用户提的表层方案拆解还原到底层真实目标、目标用户、触发频次与根本瓶颈；
   - **减法四问**：① 不做会怎样（真实损失与频次）？② 能否靠删减现有多余步骤/约束解决？③ 能否改配置或借仓库已有能力/标准库零新代码解决 80%？④ **必要性拆刀（Cut List）**：区分候选 **Must-Have（最小核）** 与疑似 **Nice-to-Have / 伪需求（候选 `Out of Scope`）**——**注意：存疑的裁剪项与 `Option 0` 必须列入第 1 轮前沿问题交用户定夺，严禁在提问前私自脑补砍掉分支而不向用户求证**。
3. **决策树多轮前沿深度追问（Design Tree + Frontier Rounds · 业务问透优先）**：
   - **建模决策树与计算当前前沿（Frontier）**：把整个计划视为一棵决策树（每个根决策下挂载依赖它的二阶、三阶子决策）。**每一轮只问完当前前置条件已落定的全部独立前沿问题**——若问题 B 的问法取决于问题 A 的答案，B 必须留到下一轮再问，绝不在同一轮硬猜前置答案。
   - **领域术语挑刺与极端场景拷问（Active Domain Grilling）**：
     1. **挑刺概念边界**：紧盯用户描述中的模糊词、一词多义或与现有 `GLOSSARY.md` 冲突的叫法发问；一旦某个领域核心词在问答中达成共识，若仓库维护 `GLOSSARY.md`（或需建立核心词表），当场写入简洁纯定义（不含实现细节），不等最后批处理；
     2. **主动构造极端反例**：不要只问正常主流程，必须针对当前前沿主动构造**并发/重入冲突、中途失败回退、空值/超限输入、权限与状态交叉**等具体边缘场景逼出隐含业务规则。
   - **固定纯文本轮次格式（全程禁用 4 题弹窗压缩）**：追问轮次**一律采用正文编号清单，不调用限 4 题的交互式多选弹窗**（彻底消除凑题数上限导致的合题与漏问），不设人为题量上限。每题按以下格式输出（措辞确保用户回复“是/默认”即代表接受推荐）：
     ```text
     ❓ **Q1 - <决策点标题>**：<具体情境、冲突点或可选项说明>
     ➡️ 推荐：<你的默认推荐方案与简明理由>
     ```
   - **多轮推进直至前沿清空（严禁把推荐当默认通过）**：给出 `➡️ 推荐` 仅方便用户按题号极速作答（如 `1 是，2 选B，3 否，原因...`），**绝不授权跳过提问**。每轮用户回复后，基于已落定答案向外重算决策树前沿，继续抛出新解锁的二阶、三阶深水区问题并等待回复；**只有当决策树所有分支均已问透、零静默假设**（或用户明确说“够了，其余按推荐进方案”提前收口）时，才结束追问进入步骤 4/5。遇到纯靠口头讨论无法判断的主观手感问题，可提议先做最小抛弃式原型预览再定。
4. **设计系统定调（仅当新建 `DESIGN.md` 或视觉改版时激活，按需先读 `references/ui-craft.md`——若路径以 `references/` 开头则相对于本 `SKILL.md` 所在目录解析；纯后端跳过）**：
   - **界面模式、第一眼记忆点 & 首屏焦点**：先锁定界面属于 **Mode A（Marketing / Persuade 叙事转化页）** 还是 **Mode B（App / Workbench 高频生产力工具台）**；在追问轮次里问清“**用户第一次看到后最该记住哪一件事？**”，按真实使用场景定明暗主题；若是官网/展示页（Mode A），同时锁定**“卖什么 + 给谁用 + 1 个硬事实 + 可工作的首要转化动作”**与真实素材来源；若是工具台（Mode B），锁定主工作区画布、固定壳层与核心高频键盘流。
   - **已有代码反推 vs 从零提案（避开默认皮肤）**：已有前端代码时先从现有样式变量/主题配置提炼草案；0→1 新建时给出 **2–3 套有明显审美差距的方向**（气质定位 + 带色相倾向的中性灰/品牌色 Token + 角色字体 Display/Body-UI/Mono + 布局密度 + 1–2 个刻意拉开差距的设计点），明令避开 AI 常见默认皮肤与静态套娃结构。
   - **视觉红线 & 自检两遍**：先写完整构图/文案骨架再自查一遍是否沦为可互换模板，严禁卡片套卡片、三栏彩色圆圈图标网格、标题上方无意义全大写小药丸、`→`/`↗` 装饰按钮、暗底霓虹光晕与假数据占位。
   - **可选静态预览**：拍板前如需眼见为实，可先生成单文件静态 HTML 样式预览页展示真实色板/字阶/组件与空错态，确认后再固化。
5. **达成共识确认与多形态备选方案对比（含 Option 0 出口）**：
   - 当决策树前沿清空后，先简要汇总已敲定的全部核心业务约定与 `Out of Scope (Cut List)`，并至少给出 **2 个结构有本质差异的实现方案**（如“最小可行” vs “更深接口封装”），标明工作量、长期维护成本、风险（含是否触及不可逆 `One-way door` 变更）、改动文件规模与推荐理由；
   - **强制保留 `Option 0`**：只要必要性存疑、收益不抵复杂度，或存在减法/零代码替代路径，**必须把 `Option 0（不做 / 删改现有流程或零代码替代）` 列为正式备选之一**；
   - **硬闸门 #1（共同理解确认 + 重大方案拍板）**：此时可用宿主交互式多选工具（≤ 4 项）或正文请用户最终确认共识并拍板选定方案（注意：用户仅回复确认总结并不等于授权直接写代码，除非处于 `/bot-auto` 编排流或用户明确要求进入下一阶段），拍板后再落盘设计文档或进入 `/bot-plan`。
6. **独立落盘模板**：
   - 设计稿默认写到 `docs/designs/<feature>.md`（或项目约定的规格目录），必含 **`Necessity / Why`（根目标与不做代价）**、追问敲定的关键边界决策与 **`Out of Scope / Cut List`（刻意不做的部分）**；
   - 新建/更新的设计系统落盘到根目录 `DESIGN.md`（结构：界面模式与记忆点 / 色彩 Tokens / 角色字体与字阶 / 间距与圆角 / 布局与五态 / 视觉红线；若用户明确只做临时草稿则记入单任务 `spec.md`）；
   - 若形成同时满足“难以逆转、无上下文会令人意外、真实权衡取舍”三条件的架构决策，写一份精简 ADR 到 `docs/adr/<NNNN>-<slug>.md`（`Context` → `Decision` → `Consequences`）。
