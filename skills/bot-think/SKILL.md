# /bot-think — 第一性原理审查与决策树多轮深度追问

目标：动代码前先验明必要性，再把需求建模为**决策树按前沿多轮挖透**，做到**零静默假设**后对齐视觉系统（若含 UI）与架构路线，落盘精简设计稿、`GLOSSARY.md`、`DESIGN.md` 或 ADR（**本阶段严禁写业务代码**）。

## 通用流控与极简铁律

1. **澄清全正文，闸门可点选**：每题附默认推荐与理由，按**交互性质**分流：
   - **需求澄清与多轮追问（不限阶段/题数）**：一律用**正文分组编号清单**（`❓ Qn` + `➡️ 推荐`，支持回“全默认，仅改第 N 题”），输出后**立即停下等回复**，**严禁调用交互式提问弹窗**，严禁自问自答或代拍板；
   - **仅三道硬闸门与最终方案拍板**：这类 1–2 项离散确认点可用宿主交互多选工具（无工具则用正文）。
2. **三道硬暂停闸门（未获明确同意严禁执行）**：
   - **重大决策**：架构路线、公开契约/Schema、不可逆 `One-way door`、删核心范围、新依赖；
   - **建分支 / worktree**：`git checkout -b` / `git switch -c` / `git worktree add` 前确认分支名与基线；
   - **发布与合并**：`git push`、建/合 PR、发版构建或上线前。
   其余探索、测试、局部重构与修 bug 连续推进。
3. **极简与反退化四铁律**：
   - **复用阶梯**：`仓库既有 helper/模式 → 语言标准库 → 平台原生特性 → 已安装依赖`，高位能解即止步，禁擅加新包；
   - **三次法则（Rule of Three）**：同一逻辑 `< 3` 次且无第二真实调用方时不抽工厂/策略/包装层；
   - **零纯转发**：禁写透传参数的 Middle Man 与不可能状态的冗余兜底；
   - **反静默退化**：边界入参显式窄化，内部不变量损坏 Fail-Fast；**禁类型逃逸（`as any` / `as unknown as T` / `@ts-ignore` / `# type: ignore`）与假默认值投毒（`?? 0` / `?? ''` / `?? []` 掩盖契约断裂）**。
4. **宿主工具**：采用宿主中立表达：读取/编辑文件、执行终端命令、代码库检索；交互式多选工具仅用于硬闸门与最终方案拍板，所有需求澄清与追问一律正文输出。

## 执行步骤

1. **事实归 Agent，决策归用户（Facts vs Decisions）**：
   - 先扫入口文档（`AGENTS.md` / `CLAUDE.md`）、`GLOSSARY.md`、`DESIGN.md` 与 `docs/adr/`；
   - 凡读代码/配置即可确认的事实，主动检索或派只读子代理查清，**严禁拿仓库已知事实烦用户**；业务规则、取舍与边界行为 **100% 归用户拍板**。
2. **第一性原理必要性审查（First-Principles Necessity Gate）**：
   - **反 XY Problem**：剥离表层方案，还原根目标、目标用户、触发频次与真实瓶颈；
   - **减法四问**：① 不做会怎样？② 能否靠删步骤/减约束解决？③ 能否靠改配置或现有能力/标准库零新代码解 80%？④ **必要性拆刀（Cut List）**：区分候选 Must-Have 与疑似伪需求（候选 `Out of Scope`）——存疑裁剪项与 `Option 0` 列入第 1 轮前沿交用户定夺，禁私自脑补砍分支。
3. **决策树多轮前沿深度追问（Design Tree + Frontier Rounds）**：
   - **按前沿多轮递进**：把需求拆成决策树，每轮只问完当前前置已落定的全部独立前沿问题；若 B 依赖 A 的答案，B 留待下一轮，绝不同轮硬猜。
   - **领域术语挑刺 & 极端反例**：
     1. **挑刺概念边界**：紧盯模糊词、一词多义或与 `GLOSSARY.md` 冲突的叫法；共识达成即向 `GLOSSARY.md` 写简洁纯定义（若最终拍板选 `Option 0`，顺手撤回仅为该废弃方案新增的未提交草稿词条）；
     2. **主动构造极端反例**：针对当前前沿构造**并发/重入冲突、中途失败回退、空值/超限输入、权限与状态交叉**等场景逼出隐含规则。
   - **固定纯文本格式（全程禁用提问弹窗）**：所有追问轮次一律正文编号输出，不设题量上限，确保用户回“是/默认”即接受推荐：
     ```text
     ❓ **Q1 - <决策点标题>**：<具体情境、冲突点或可选项>
     ➡️ 推荐：<默认推荐与简明理由>
     ```
   - **推进至前沿清空（零静默假设）**：`➡️ 推荐` 只为方便用户按题号极速答复，绝不授权跳过提问。每轮回复后重算前沿抛出新解锁的二/三阶问题，直至决策树所有分支问透（或用户明确口令“够了，其余按推荐进方案”提前收口）。纯主观手感问题可提议最小抛弃式原型预览再定。
4. **设计系统定调（仅新建 `DESIGN.md` 或视觉改版时激活，先读 `references/ui-craft.md`——`references/` 相对本 `SKILL.md` 目录；纯后端跳过）**：
   - 按 `ui-craft.md` 锁定 **Mode A（Marketing）** 或 **Mode B（Workbench）**，在追问中问清“**用户第一眼最该记住哪一件事？**”（第一眼记忆点）与明暗主题；
   - 已有前端代码先反推现有样式变量；0→1 新建给 **2–3 套差异明显的视觉方向**（气质、tinted gray/品牌色 Token、角色字栈、布局密度与 1–2 个拉开差距的设计点），严守 `ui-craft.md` 反套路红线并自检两遍；需要时可先生成单文件静态 HTML 预览板确认。
5. **共识确认与结构化备选对比（含 Option 0）**：
   - 前沿清空后，汇总已敲定的业务约定与 `Out of Scope (Cut List)`，给出至少 **2 套结构本质不同的实现方案**（工作量、维护成本、改动规模、是否含不可逆 `One-way door` 风险与推荐理由）；
   - 只要必要性存疑或存在减法/零代码路径，**强制保留 `Option 0（不做 / 删改现有流程或零代码替代）`**；
   - **硬闸门 #1**：可用宿主交互多选工具或正文请用户确认共识并拍板方案（确认总结不等同于授权直接写代码，除非处于 `/bot-auto` 或用户明示进入下一阶段）。
6. **独立落盘模板**：
   - 设计稿写 `docs/designs/<feature>.md`（或规格目录），必含 `Necessity / Why`、关键边界决策与 `Out of Scope / Cut List`；
   - 设计系统写根目录 `DESIGN.md`（模式与记忆点 / 色彩 Tokens / 角色字阶 / 间距圆角 / 布局五态 / 视觉红线）；
   - 同时满足“难逆转、无上下文会意外、真实权衡”的架构决议写精简 ADR 到 `docs/adr/<NNNN>-<slug>.md`（`Context → Decision → Consequences`）。
